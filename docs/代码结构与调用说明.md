## 先看这张职责表

| 层次 | 位置 | 回答的问题 | 不承担的事情 |
|---|---|---|---|
| 配置 | `config.py` | 请求哪个环境、默认超时多少、管理员账号是什么 | 不发送请求 |
| 通用请求 | `core/api_client.py` | 如何检查路径、拼接地址、转发参数和发送 HTTP | 不判断业务成功 |
| 业务接口 | `apis/` | 某个业务操作使用哪个方法、路径和请求体 | 不创建测试数据，不写业务断言 |
| 测试准备 | `conftest.py` | 使用谁的身份、准备什么数据、结束后如何恢复 | 不代表所有 fixture 都会自动执行 |
| 场景与断言 | `tests/` | 本次要验证什么，预期结果是什么 | 不重复拼接完整服务地址 |
| 数据驱动 | `data/`、`data_loader.py` | 哪些参数化输入和预期允许进入测试 | 不发送接口请求 |
| 运行配置 | `pytest.ini` | 允许哪些标记、默认附加哪些选项 | 与业务环境配置不同 |

## 两条线必须分开理解

### 准备对象：fixture 的依赖关系

Pytest 看测试函数形参，寻找同名 fixture，再递归准备它依赖的 fixture。文件中函数的书写先后不是执行顺序。

普通管理端客户端：

```text
api_session → api_client → auth_api
              ↑
       base_url / request_timeout
```

已登录管理端对象：

```text
api_client + auth_api + login_payload
                ↓
           admin_client
                ↓
admin_auth_api / admin_apartment_api / admin_room_api
admin_tenant_api / admin_lease_api
```

`admin_client` 返回的就是登录后设置请求头的 `api_client`，不是新客户端。若同一测试同时依赖二者，会看到相同 Session 的令牌。匿名场景不要再依赖 admin_client。

租客端使用另一套独立 Session：

```text
tenant_client → tenant_auth_api
       ↓              ↓
       └── created_tenant ──→ logged_in_tenant_client
                                      ↓
                                tenant_room_api
```

其中 created_tenant 的建档和清理仍由管理员完成。租客请求者与租客资料的操作者是两个角色，不能因为数据是“租客”就全部使用租客客户端。

### 真正发请求：方法的调用关系

以租客登录为例：

```text
测试：tenant_auth_api.login(payload)
  ↓
TenantAuthApi：确定 POST /tenant-app/auth/login，使用 json 请求体
  ↓
ApiClient：检查相对路径、拼接 BASE_URL、补默认 timeout
  ↓
Requests Session：向后端发送请求
  ↓
Response 返回给测试，测试解析 JSON 并断言
```

对象准备和接口执行是两件事。例如 `RoomApi(client)` 只保存客户端，不会自动查询房间。

## conftest.py 阅读导航

| 分类 | fixture | 作用 |
|---|---|---|
| 配置输入 | `base_url`、`request_timeout` | 把 config.py 的值交给请求客户端 |
| 普通管理端请求 | `api_session`、`api_client`、`auth_api` | 提供基础会话和未提前登录的接口对象 |
| 管理员身份 | `login_payload`、`admin_client` | 正确登录并保存管理员 Bearer 请求头 |
| 管理员业务对象 | `admin_auth_api`、`admin_apartment_api`、`admin_room_api`、`admin_tenant_api`、`admin_lease_api` | 在同一管理员客户端上包装业务方法，不各自重复登录 |
| 登录状态恢复 | `login_state` | 密码失败测试前后正确登录，清除失败计数 |
| 基础业务数据 | `created_apartment`、`created_room`、`created_tenant` | 创建本次数据，并只处理本次 ID |
| 入住关联 | `lease_payload`、`created_lease` | 组装租客与房间关联、办理入住、最后退房并核对状态 |
| 租客会话 | `tenant_client`、`tenant_auth_api` | 独立会话，不携带管理员令牌 |
| 已登录租客 | `logged_in_tenant_client`、`tenant_room_api` | 为后续租客业务提供身份 |

所有 fixture 当前默认 function 作用域：同一测试内同名 fixture 只准备一次；不同测试重新创建。参数化展开的每组数据也各是一条测试。

在测试形参声明 fixture 即可触发准备，不必在函数体手动调用它。不要给身份 fixture 随意加 autouse，否则匿名/拒绝场景会被自动登录。

### yield 和 return 的差别

- `return`：把已经准备好的对象交给测试，本函数没有后半段清理。
- `yield`：把对象交给测试，测试结束后继续执行后面的清理。
- `try/finally`：测试断言失败也会尝试清理；进程被强制结束等情况不保证能完成清理。
- `with requests.Session()`：关闭的是客户端连接资源，不是服务端登录状态。

`admin_client` 用 return 也能关闭会话，因为其依赖 api_session 用 with/yield 负责资源生命周期。

## 数据创建与结束顺序

```text
创建公寓 → 创建房间 ──┐
                      ├→ lease_payload → 创建入住 → 测试
创建租客 ─────────────┘
```

结束时先结束依赖方：

```text
退房并检查房间/入住记录状态
             ↓
清理本次租客、房间（不同分支的相对先后不必假定）
             ↓
房间清理完成后，清理所属公寓
```

房间逻辑删除后查询应返回“房间不存在”，公寓同理。退房不同：租约变为已退房且保留历史，账单也不是通过退房删除。

入住会触发后端按该业主和月份生成账单，当前测试只验证相关入住/退房状态，不宣称数据库完全恢复到无历史的状态。

## 三种对象和两种状态编号

```python
response = api.create(payload)   # Requests Response
body = response.json()          # Python dict
item = body["data"]              # 具体数据，可能是 dict/list/None
```

- HTTP 状态读取 `response.status_code`，业务码读取 `body["code"]`。
- Response 没有字典的 `.get()`，应在解析后的 body 上调用。
- `.get("data")` 可兼容失败响应省略 data 字段；必填成功字段则应明确检查。
- HTTP 200 不能替代业务成功断言：当前后端若干失败响应仍返回 HTTP 200。

| 资源 | 状态值 |
|---|---|
| 房间 | 0 空置、1 预定、2 在住、3 维修 |
| 入住记录 | 0 在住、1 已退房 |

在住房间 status=2，关联入住记录 status=0；退房后房间 status=0，入住记录 status=1。断言前先辨认查询的资源。

## YAML 如何进入测试

```text
data/login_cases.yaml
        ↓ safe_load
列表，每条为一个字典
        ↓ data_loader.py
检查结构、字段、类型和唯一编号
        ↓ pytest.mark.parametrize
每个 case_id 形成独立测试名称
        ↓
测试从 case 取输入和预期，调用 AuthApi 并断言
```

加载发生在测试收集阶段；数据错误会导致模块收集报错。密码要写字符串，空密码应写 `""`。不要在 YAML 中保存真实账号密码或令牌。
