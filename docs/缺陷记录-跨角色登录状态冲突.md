# D04：租客与系统用户相同数字 ID 导致跨角色令牌失效

- 状态：待修复；本次仅记录和收尾测试数据，未修改后端、Redis 命名规则或部署。
- 日期：2026-10-25。
- 影响：不同角色互相登录失效，租客业务请求 HTTP 401，报修 fixture 无法按 API 正常取消工单。

## 本轮证据

账单模块先独立执行 12 passed in 5.74s。随后完整执行 76 条，Pytest 汇总为 72 passed、4 failed、11 errors in 34.70s，其中一个失败是已知 D03。其余业务失败和后置错误均在租客请求收到 401 时发生。Allure 按最终测试状态归并为 64 passed、12 failed：部分用例调用阶段通过但清理阶段失败，因此与 Pytest 的分阶段计数不同。

只读检查发现，本轮工单对应租客 ID 417～427；这些数字同时存在于本轮 auto_worker 系统账号中。例如工单 243 的 tenant_id=418、handler_id=418、assignee_id=418；工单 247 对应三者均为 422。它们代表不同表中的不同主体，数值相同不能视为同一身份。

## 源码定位

- TenantAuthServiceImpl.login 调用 removeUserTokens(tenant.getId())，并用 tenantId 存储访问/刷新令牌。
- WorkerAuthController.login 同样调用 removeUserTokens(user.getId()) 并存储系统用户令牌。
- RedisTokenService 使用 user_token:{id}、user_access_tokens:{id}、user_refresh_tokens:{id}，未包含身份域。
- removeUserTokens 依照上述集合删除旧 access_token 记录；TenantJwtAuthenticationFilter 查询不到该记录便返回 HTTP 401。

因此两个表的数字 ID 重合时，后登录的角色会删除另一个角色的登录状态。现有独立 Session 不能避免服务端 Redis 键冲突；本次新增双租客数据改变了自增进度，使既存问题在全量中被触发。不可通过修改断言接受 401、重置自增值、反复重跑至偶然不重合来掩盖。

## 可复现条件与预期

准备数值 ID 相同的租客和维修工，租客先登录，再登录维修工，随后租客请求自己的受保护接口。预期不同身份域互不下线；当前登录实现会移除同数字 ID 的令牌。首次全量已通过真实失败、数据库 ID 重合与源码调用链定位；现已增加下面的 API 专项回归，不插入指定主键或修改自增值。

## 修复方向与回归建议

后续应按身份域区分租客和系统用户的单点登录映射/集合，并同步登录、刷新、登出、校验及令牌撤销逻辑；不能仅改一个登录入口。修复后应专门覆盖相同数值 ID 的跨角色登录并保持各自会话有效，再执行完整回归。后端修复尚未实施。
