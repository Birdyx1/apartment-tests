# MCP 辅助接口测试工作流

## 目标

MCP 为测试助手补充可调用的上下文和证据来源，例如从实际页面观察请求、查看当前 PR 的 CI 诊断。它不替代 `pytest`、Allure、项目 API wrapper 和人工确认的接口预期，也不需要把 MCP 客户端依赖加入被测 Python 项目。

## 当前可用能力与适用范围

| MCP 能力 | 本项目用途 | 使用边界 |
|---|---|---|
| Playwright 浏览器与网络工具 | 从管理端/租客端/维修工端页面定位用户动作触发的 API 方法、路径和状态码；辅助检查页面与接口链路 | 只在需要时访问本地测试环境；默认只看请求摘要，不取 Authorization、Cookie、验证码内容或完整个人数据；浏览器观测是运行事实，不自动成为需求 |
| Code Review / CI 诊断工具 | PR 在代码托管平台上已有构建时，读取对应 revision 的检查结果 | 先核实 PR、revision 和构建身份；只读结果，不把旧构建作为当前证据，不自动写评论或修改 PR |
| ADB MySQL 查询工具 | 仅当用户指定隔离的 ADB 测试库且确有只读排查需求时提供数据上下文 | 本项目当前主要运行在本机 Docker MySQL；不默认连接云库、不访问生产数据、不执行写入；数据库结果不能取代 API 契约断言 |

工具是否可用由当前 Codex 会话决定。每次任务开始先检查工具清单；没有对应 MCP 时，继续用仓库文档、后端源码和现有测试完成工作，并标明证据来源。

## 推荐闭环

1. 先明确测试范围与目标角色，查看 `WIKI.md`、测试矩阵、相关 API wrapper/fixture、Controller 和 DTO。
2. 若接口路径或页面动作不清楚，再用 Playwright MCP 打开本地前端，读取可访问性快照并按 API 路径过滤网络请求。避免因为“页面发出了请求”就断定接口返回符合预期。
3. 分别记录需求/文档、后端实现、MCP 运行观测和人工确认预期。发现冲突时保留未决项，不自行把某一来源升格为产品契约。
4. 由 Skill 生成少量高价值测试草稿，检查请求字段、身份与数据归属、清理顺序、敏感信息处理和断言强度；使用现有 `ApiClient`、wrapper、fixture 与 `assert_response`。
5. 先运行定向 Pytest，再根据改动范围决定是否运行全量。结合 Allure/Jenkins 当前结果归类为产品缺陷、测试代码、环境或数据清理问题。
6. 把结论、证据日期、未决问题和下一步写回 `WIKI.md` 与评估报告；不要让 AI/MCP 自动删除缺陷用例、降低断言、提交或部署。

## 本机验证记录

2026-10-25 在当前 Codex 会话中通过 Playwright MCP 访问 `http://localhost:3000`，页面落在 `/login`，标题为“智能公寓系统”。按 `/auth|captcha` 过滤网络请求，观测到 `GET http://localhost:8080/auth/captcha` 返回 HTTP 200。此次只记录方法、路径和状态码；未读取验证码响应体、请求头、Cookie 或登录凭据。

这证明当前会话的 Playwright MCP 可以为本机系统提供页面到 API 的运行证据。它没有验证登录业务，也没有把 HTTP 200 推断为验证码契约正确；后续需结合 `AuthController`、DTO 和确认后的需求设计断言。

## 当前工具选择

- 接口测试补充：Pytest/Requests 是执行与断言主体；Playwright MCP 是可选的浏览器流量发现工具。
- Jenkins 与 Allure：继续使用项目现有流水线与报告流程。PR/CI MCP 只在需要分析具体构建时使用。
- MySQL MCP：当前不接入测试执行链路。项目已有 API fixture 管理业务数据，且 MCP 连接的是 ADB MySQL 能力，和本机 Docker 测试库不是同一目标。
