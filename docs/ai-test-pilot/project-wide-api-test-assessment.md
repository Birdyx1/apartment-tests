# 全项目接口自动化评测与后续 AI 赋能路线

- 日期：2026-10-25。
- 范围：`apartment-tests` 当前 Pytest/API 框架及对应 Smart Apartment 后端控制器。
- 方法：使用 `apartment-api-test-assistant` 盘点测试模块、封装和后端 controller mapping；浏览代表性测试与 CI 历史记录。
- 评测边界：这是全项目级静态盘点，不是对全部收集用例逐行审查，也不是后端所有接口的契约认证。

## 全项目结论

1. 测试框架已经覆盖项目主要租住与维修流程，并有客户端、API wrapper、fixture、统一断言、失败证据、Jenkins/Allure 等基础设施。当前收集 109 条；收集数量本身不是覆盖率结论。
2. 覆盖深度不均：维修工单和租金支付场景较深入；系统配置管理、通知、仪表盘、支付回调、非维修工文件入口和部分管理端 CRUD 需要评估。
3. API 文档是当前 AI 自动化生成的主要瓶颈：发现的 OpenAPI 文件只描述公寓模块。其他 Controller 可用于核对实现路径，但不能单独作为预期业务行为。应优先建立经人工确认的轻量接口事实表，而不是直接从 Java 生成“正确答案”。
4. 已知 D03/D04 缺陷仍按此前要求保留。AI 输出应携带证据并建议归因，不能自动修改产品逻辑、删除用例、降低断言或宣称全绿。
5. 最新全量运行 `python -m pytest -q --tb=no` 时收集 110 条，结果为 `105 passed, 5 failed in 53.94s`。5 条失败均可归类：D03 派单取消后指派人未清空 1 条；D04 相同数字 ID 的租客/维修工登录会撤销另一身份令牌 2 条；用户列表和详情返回 `password` 字段 2 条。D03/D04 依此前要求保留；密码字段问题为安全缺陷证据。其余 105 条通过，租客更新、重复身份证号拒绝、密码管理与跨管理员归属新增测试均通过。
