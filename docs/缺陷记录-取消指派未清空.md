# D03：取消指派返回成功，但指派人未清空

- 状态：待修复；学员于 2026-10-25 明确要求暂不修复，保留失败回归用例并继续其他场景。
- 发现日期：2026-10-25。
- 环境：当前本地后端，API 基础地址 http://localhost:8080。
- 回归用例：tests/test_admin_maintenance.py::test_admin_cancel_assignment_success。

## 复现与证据

1. 创建待处理报修工单，并创建启用的维修工账号。
2. 管理员 PUT /maintenance-order/{id}/assign，JSON 为 {"assigneeId": 维修工ID}；响应 HTTP/业务码 200、data=true。
3. 租客查询详情，确认状态 0、assigneeId 为该维修工。
4. 管理员调用同一接口，JSON 为 {"assigneeId": null}；仍返回 HTTP/业务码 200、data=true。
5. 再次查询详情，assigneeId 仍为原维修工。

本次实际工单 ID 192，维修工 ID 345；断言 `order["assigneeId"] is None` 失败，实际值为 345。单条执行结果：1 failed in 0.57s，无后置 ERROR；工单后置取消、账号与其他资源清理已正常完成。

## 预期与实际

控制器接口说明明确 assigneeId 为空表示取消指派。预期工单仍为状态 0，assigneeId 为 null。实际响应成功，但详情仍保留指派关系。

## 初步定位

MaintenanceOrderServiceImpl.assignOrder 使用 order.setAssigneeId(assigneeId) 后 updateById(order)。MaintenanceOrder.assigneeId 未配置空值更新策略，已读全局配置中也未显式设置该策略。怀疑实体空字段被更新策略跳过；尚未通过实际 SQL 或修复回归最终确认。

建议在该业务方法中显式更新 assignee_id（包括 NULL），避免为所有字段全局开启空值更新；保留现有所有权、状态与维修工资格校验。后端源码和运行镜像本次均未修改。

## 测试侧处理

已修正用例：首次 assign(order_id, worker_id) 建立真实指派，第二次 assign(order_id, None) 清除指派；移除不存在的 cancel 方法调用。保留清空断言作为失败回归证据，不改为允许原指派人，也不以忽略或跳过隐藏缺陷。
