# 任务书 01：租客报修接口自动化

日期：2026-10-24。状态：待独立设计与实现。

本任务采用“任务书 → 学员设计并编码 → 导师审查 → 执行与复盘”的方式，不提供测试代码答案。文档根据本地后端源码整理，不是新一轮接口实测结果。现有项目基线可收集 21 个场景。

## 1. 业务目标与本轮边界

完成：管理员准备租客及入住房间 → 租客登录 → 申请报修 → 查看详情和本人列表 → 取消 → 确认状态正确 → 退房及清理基础资料。

同时覆盖未入住拒绝、必填项校验、重复取消。你自行决定接口方法、fixture、测试数据及参数化的组织方式，并说明选择理由。

本轮不做维修工派单/抢单/完工、图片上传、真实支付、并发和跨租客越权。它们不是已覆盖，也不作为本轮交付门槛。图片字段使用空列表或省略。

## 2. 可复用资产与身份

| 已有组件 | 用途 |
|---|---|
| ApiClient | 相对路径、服务地址、超时、日志、HTTP 发送 |
| logged_in_tenant_client | 已登录租客的独立客户端 |
| created_tenant | 唯一模拟租客及本地密码 |
| created_apartment / created_room | 独立公寓与房间 |
| created_lease | 管理员办理入住，结束时退房并核对恢复 |
| tenant_auth_api / tenant_room_api | 租客登录与本人房间能力，可按需复用 |

报修接口的调用者是租客，使用租客访问令牌；管理员只负责前置资料及入住。接口对象构造本身不应创建工单或隐式办理入住。

同一测试中的同名 fixture 会缓存复用，确保入住租客、登录租客和申请工单的租客一致。未入住场景不能依赖任何会隐式准备 created_lease 的组件。

## 3. 接口公共约定

- 默认基础地址：http://localhost:8080，以 config.py 为准。
- 把下列相对路径交给 ApiClient，不在接口层再次拼接 BASE_URL。
- 身份：已登录租客，`Authorization: Bearer <租客访问令牌>`。
- 创建请求体：JSON，Content-Type 为 application/json。
- HTTP 状态码与 JSON 业务码分层检查；不要把业务码 400/500 当成 HTTP 400/500。
- 成功业务码 200，通常 message 为“操作成功”。失败时空 data 可能被省略，不能假定键始终存在。
- 下方 ID 和响应为结构示例，不可硬编码成环境预期值。

### 3.1 申请报修

**POST /tenant-app/maintenance/create**

前置：租客已登录，且存在有效的在住记录。后端从令牌与当前入住关系推导 roomId/tenantId，请求不需要也不应依赖传入这些字段。

| JSON 字段 | 类型 | 必填 | 当前约定 |
|---|---|---|---|
| title | string | 是 | 非空、不能只有空白；测试标题包含唯一标识 |
| description | string | 否 | 问题描述，便于核对原值 |
| urgency | integer | 是 | 业务说明为 1 普通、2 紧急、3 非常紧急 |
| imageKeys | array of string | 否 | 已上传图片 objectKey，本轮空列表或不传 |

请求示例：

```json
{
  "title": "自动化报修-唯一标识",
  "description": "卫生间水管漏水",
  "urgency": 1,
  "imageKeys": []
}
```

成功：HTTP 200，业务码 200；data.id 为新建工单正整数 ID，初始工单状态为 0（待处理）。

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {"id": 123},
  "success": true
}
```

相关失败约定：

| 触发条件 | HTTP | 业务码 | 提示检查 |
|---|---:|---:|---|
| 已登录但未入住，请求其余字段有效 | 200 | 400 | 等于“您当前没有在住记录，无法申请工单” |
| title 为空字符串或仅空白，其余条件有效 | 400 | 400 | 包含“工单标题不能为空” |
| urgency 字段缺失或为 null，其余条件有效 | 400 | 400 | 包含“紧急程度不能为空” |

验证错误提示含义，不绑定字段错误拼接顺序、分号或尾部空格。失败均不应返回新建工单数据。

实现差异：当前 DTO 只对 urgency 做非 null 校验，没有枚举范围校验；不要凭空写“urgency=0 必须被当前实现拒绝”。本轮只测试正常范围与缺失。imageKeys 超限错误发生在工单保存之后，本轮不测试图片异常，避免把它混入基础场景。

### 3.2 工单详情

**GET /tenant-app/maintenance/{id}**

路径 id 是工单 ID，不是房间或租约 ID。当前租客只能查看自己申请的工单。

成功：HTTP 200、业务码 200，data 为详情对象。本轮字段如下：

| 字段 | 含义与检查用途 |
|---|---|
| id | 与创建响应 ID 相同 |
| roomId | 与本次入住房间一致 |
| tenantId | 与本次登录租客一致 |
| title / description / urgency | 与创建输入一致 |
| status | 初始 0，取消后 3 |
| apartmentId | 可用于进一步核对所属公寓 |
| logs | 处理时间线，当前任务不强制逐条断言 |

```json
{
  "code": 200,
  "data": {
    "id": 123,
    "roomId": 45,
    "tenantId": 67,
    "title": "自动化报修-唯一标识",
    "description": "卫生间水管漏水",
    "urgency": 1,
    "status": 0,
    "apartmentId": 8
  }
}
```

注意：字段列表不是完整 schema。示例省略了额外字段，不能要求真实响应只包含示例键。

补充错误说明（不作为本轮必做场景）：他人工单返回 HTTP 200、业务码 403、“无权访问该工单”。不存在工单会在当前 service.getDetail 中先抛异常，现实现为 HTTP 200、业务码 500、“工单不存在”，不能仅根据 controller 中后置空值判断推断为 400。

### 3.3 本人工单列表

**GET /tenant-app/maintenance/list**

无需分页参数。成功 HTTP 200、业务码 200，data 直接是详情对象列表，不是 data.records。

```json
{
  "code": 200,
  "data": [{"id": 123, "roomId": 45, "tenantId": 67, "status": 0}]
}
```

目标检查：按本次 order_id 匹配，恰好一条；归属租客与房间正确；取消后记录仍在且 status=3。新建租客未申请过任何工单时可检查空列表，不能对共享账号列表硬编码总长度。

### 3.4 取消工单

**PUT /tenant-app/maintenance/{id}/cancel**

不需要请求体。仅本人待处理或处理中工单可取消。取消不等于删除，不等于完成维修，也不等于退房。

成功：HTTP 200、业务码 200、data=true；工单状态变为 3。

```json
{"code": 200, "message": "操作成功", "data": true}
```

| 触发条件 | HTTP | 业务码 | message |
|---|---:|---:|---|
| 取消自己的待处理工单 | 200 | 200 | 操作成功 |
| 再次取消已取消工单 | 200 | 500 | 只能取消待处理或处理中的工单 |
| 工单不存在（补充说明） | 200 | 400 | 工单不存在 |
| 他人工单（补充说明） | 200 | 403 | 无权取消该工单 |

重复取消失败后，详情应仍为 3，不应回到 0/1。

## 4. 必做场景矩阵

至少覆盖以下六个独立场景。测试函数数可按合理参数化调整，不要求机械地一行对应一个函数。

| 编号 | 优先级 | 场景 | 主要验收断言 |
|---|---|---|---|
| M01 | P0 | 在住租客申请报修并查询 | 创建成功且正整数 ID；详情准确关联租客/房间；输入字段一致；status=0；本人列表按 ID 唯一包含它 |
| M02 | P0 | 取消本人待处理工单 | 取消成功且 data=true；详情和本人列表均显示 status=3；历史仍在，不误断言不存在 |
| M03 | P1 | 已登录、未入住租客申请报修 | 请求字段有效；HTTP 200/code 400/明确提示/无 data；本次租客列表保持为空 |
| M04 | P1 | title 为空，其他前提有效 | HTTP 400/code 400/必填提示/无 data；未创建工单，列表数量未增加 |
| M05 | P1 | urgency 缺失，其他前提有效 | HTTP 400/code 400/必填提示/无 data；未创建工单，列表数量未增加 |
| M06 | P1 | 已取消工单再次取消 | 第二次取消返回约定拒绝；查询仍为 status=3，原 ID/租客/房间不变 |

M04/M05 使用在住租客，保持其他业务前提有效，仅改变一个参数。不能因为未入住和空标题同时错误，就认为明确覆盖了标题校验场景。

M02/M06 的取消操作及核心断言必须出现在测试步骤中。不能只在 teardown 取消成功，就将独立的“取消功能用例”算作已实现。

## 5. 设计与清理要求

1. 复用现有 ApiClient、身份与基础数据 fixture；业务路径集中封装，测试保留业务断言。
2. 为本次租客创建唯一标题，所有详情/列表检查都使用本次创建的真实 ID，不使用种子数据或他人工单。
3. 你自行设计数据 fixture 的返回值与依赖，并能解释“谁登录、谁入住、谁取消”。未入住与参数非法场景不要误依赖会提前创建有效工单的 fixture。
4. 工单创建成功取得可靠 ID 后立即安排异常情况下的恢复；测试断言失败也要尝试处理本次工单。
5. 清理顺序：处理/取消本次工单并确认终态 → 退房 → 删除临时租客与房间 → 删除所属公寓。利用 fixture 依赖保证顺序，不依赖测试排列。
6. 清理前先确认状态：0/1 可取消；如果测试已取消并且是 3，验证后跳过再次取消。不要盲目再取消，造成正常用例的 teardown ERROR；不要用无条件忽略异常掩盖真正清理失败。
7. 取消保留工单和操作日志历史；退房保留租约及账单历史。本轮不做物理清库，不清空数据库或 Redis，不宣称无历史残留。
8. 不改变现有数据 fixture 的契约来让其他测试被自动入住或自动报修；不同场景的前置条件应明确。
9. P0/P1 注册方式沿用 pytest.ini；提供清楚的 Allure 中文标题，日志不输出密码、令牌和完整身份数据。
10. 接口返回与文档不同，先记录请求方法/路径、脱敏输入、HTTP/业务码、提示和实际副作用，定位是代码错误、环境差异还是业务缺陷；不放宽断言只为变绿。
