# 租客报修测试设计

日期：2026-10-24。根据学员的 fixture 理解、现有代码与实际运行结果整理；接口约定见[任务书 01](任务书01-租客报修自动化.md)。

## 场景与断言

| 编号 | 优先级 | 场景 | 核心检查 |
|---|---|---|---|
| M01 | P0 | 在住租客创建报修 | 创建得到正整数 ID；详情的内容和租客/房间归属正确；本人列表按 ID 唯一包含该工单；状态为 0 |
| M02 | P0 | 取消本人待处理工单 | 取消返回成功及 data=true；详情、本人列表状态均为 3；历史工单仍在 |
| M03 | P1 | 未入住租客申请报修 | HTTP 200、业务码 400、明确未入住提示、无 data；本人列表为空 |
| M04 | P1 | 空字符串或纯空格标题 | 参数化执行两次；HTTP/业务码均为 400、必填提示、无 data；本人列表为空 |
| M05 | P1 | 缺失 urgency | 复制有效数据后删除该字段；HTTP/业务码均为 400、必填提示、无 data；本人列表为空 |
| M06 | P1 | 已取消工单再次取消 | 第一次成功，第二次 HTTP 200/业务码 500；明确拒绝且无 data；原 ID、租客、房间不变，状态仍为 3 |

六类场景共执行 7 条，测试位于 tests/test_tenant_maintenance.py。参数校验场景使用已入住租客，只改变一个字段，避免同时存在未入住与字段非法两个原因。

## 身份与 fixture 职责

- tenant_maintenance_api：提供携带租客令牌的接口对象，支持 create/detail/list/cancel；构造对象不自动创建工单。
- logged_in_tenant_client：使用本次 created_tenant 登录，并给独立的租客 Session 设置令牌，与管理员 Session 分离。
- maintenance_payload：只组装有效请求字典，标题包含唯一标识；异常测试复制字典后修改。
- created_lease：管理员为本次租客和房间办理入住，返回关联信息，结束时退房并检查恢复。
- created_maintenance：依赖已入住前提，创建工单；yield 返回工单与关联 ID，finally 尝试取消并核对状态。

依赖关系：created_maintenance 依赖 created_lease、tenant_maintenance_api、maintenance_payload；接口对象通过 logged_in_tenant_client 依赖 created_tenant，入住也依赖同一个 created_tenant。同一条测试内 Pytest 缓存同名 fixture，保证入住和登录对应同一租客。

未入住测试只使用租客接口对象和有效请求数据，不依赖 created_lease 或 created_maintenance。只要在测试形参中声明 fixture，即使不读取返回值，也会触发它的准备流程。

## 清理与状态恢复

先处理工单并确认状态 3，再退房，然后清理临时租客、房间及公寓；房间必须先于所属公寓清理。fixture 依赖保证工单清理先于入住 fixture 的退房，不能依赖测试函数排列。

清理先查工单详情：状态 0/1 执行取消；状态 3 跳过重复取消；其他状态明确报错。最后复查状态为 3。测试断言失败也会进入 finally；清理请求或断言失败会暴露为错误，不忽略异常。

创建报修要求当前在住。当前取消接口校验登录身份、工单归属与工单状态，不检查入住状态，因此不能推断“退房后接口一定不能取消”。先取消再退房是本测试的恢复顺序，让工单先达到明确终态，再拆除入住等前提。

取消保留工单及操作日志，退房保留租约和账单历史；本测试不物理清库，也不清空 Redis。
