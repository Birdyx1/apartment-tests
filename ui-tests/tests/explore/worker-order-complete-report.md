# 维修工端完成工单表单：用例矩阵与探索报告

## 范围与测试数据

- 页面：维修工 H5 工单详情中的“完成工单”表单。
- 所有用例使用独立维修工与唯一临时业务链。准备阶段由该维修工抢单进入处理中，再打开完成表单。
- 终态清理：工单完成后保留完成历史；处理中用例由管理员取消。两者都先退房、验证房间空置，再删除可删除依赖和维修工账号。
- 图片上传会单独验证 UI 选择和完成请求。本测试可隔离上传存储：上传控件使用临时响应，实际完成请求仍调用本地后端；上传 API 本身由接口测试覆盖，避免每次 UI 回归在 MinIO 留下孤立对象。

## CLI 探索和执行记录

- 有头 CLI 从待抢列表打开唯一工单，按“抢单”并确认进入处理中，再打开完成工单表单。表单包含备注框、图片上传和“确认完成”按钮；备注框按 placeholder 定位，确认按钮按 role/name 定位，图片选择通过可访问的“上传”按钮触发 file chooser。
- 空表单点击确认显示“请填写处理备注”；填写备注但无图片显示“请至少上传一张处理图片”。两项校验都留在表单中，不发送完成请求，后端工单状态仍为 1。
- 成功路径上传一张合成 PNG 并填写处理备注，完成请求 `PUT /worker-app/maintenance/{id}/complete` 返回 HTTP 200，随后详情 GET 返回 HTTP 200。页面状态变为“已完成”，显示处理图片区、备注与完成记录，操作按钮消失；后端 status=2、handlerId 为当前维修工，备注及一张处理图片均已保存。
- UI 测试通过 Playwright route 为上传接口提供临时成功响应，不向 MinIO 留孤立对象；完成请求仍真实调用本地后端并验证保存的数据。图片上传接口另由 API 测试覆盖。测试图片为 `tests/fixtures/completion-image.png`。
- 新增 `tests/test_worker_order_complete.spec.ts`；扩展 `worker-detail-data.fixture.ts` 支持 status=2 已完成终态：不取消已完成工单，退房并核验房间空置后清理可删除依赖。WC-001 至 WC-003 单独对应三个 `test()`。
- 完成表单定向运行 **3 passed（6.8s）**；随后维修工端详情、抢单、完成、待抢和我的工单回归共 **12 passed（12.9s）**。每条用例都有截图、视频和 Trace，保存在 `test-results/`。
- headed 探索的临时工单保持为已完成历史；租约已退房，房间核验为空置，临时房间/公寓/租客和维修工账号已清理。
