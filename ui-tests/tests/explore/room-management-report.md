# 房间管理：测试设计与探索报告

## 输入与范围

- 场景来源：上一页面公寓管理之后的管理端路由 `/rooms`。
- 起始 URL：`http://localhost:3000/rooms`。
- 前置条件：管理员已登录；使用项目忽略的 `tests/explore/apartment-list-auth.json` 登录态。
- 用例矩阵先按路由和页面源码形成，控件名称、交互和反馈需经 Playwright CLI 实际探索后确认。
- 所有写操作使用唯一房间号；测试结束删除自己创建的房间，不修改已有房间。
- 创建房间需要所属公寓；探索阶段核对下拉选择方式和可用数据。正式用例应从页面可见选项中动态选取公寓，不固定公寓名称或 ID。

## 探索记录

- 通过项目 `playwright-cli` 有头会话打开 `/rooms`。未登录直接访问会跳转 `/login`；加载 `tests/explore/apartment-list-auth.json` 后成功进入房间管理页。
- 页面实际表头为“公寓、房间号、楼层、户型、面积(㎡)、状态、更新时间、操作”；筛选区含公寓远程选择、房间号、楼层、状态、搜索和重置；列表上方含“新增房间”和“刷新”。
- “新增房间”弹窗字段为公寓、房间号、楼层、户型、面积(㎡)、状态、描述；前六项必填。空表单提交后实际出现“请选择公寓”“请输入房间号”“请输入楼层”“请选择户型”“请输入面积”“请选择状态”。
- 公寓远程下拉按输入查询；探索时当前返回多个可选公寓。正式测试选择页面返回的首个可见 option，不写死名称或 ID。户型/状态是下拉选项，实际观察到“一房一厅”“空置”等选项。
- 使用唯一房间号 `UI-RM-EXPLORE-20261025` 创建房间，页面显示“创建成功”并在列表显示该行；按房间号搜索后只显示目标行。删除时显示“确认删除该房间？”确认框，确认后显示“删除成功”，该探索数据已清理。
- 编辑临时房间时，面积字段未回显创建时的 35。源码核对发现 `ApartmentRoomController.toVO` 未把 `room.area` 写入 `RoomListVO`（`vo.setArea(room.getArea())` 当前被注释）；而编辑表单将面积设为必填，导致现有房间编辑存在阻塞风险。此处只新增缺陷回归，不修改后端。
- 可访问性快照保存在 `room-management-snapshot.md`、`room-management-create-snapshot.md`、`room-management-validation-snapshot.md` 和 `room-management-filter-snapshot.md`。CLI 截图命令两次因等待页面稳定超时，未产生探索截图；后续 Playwright Test 自动截图/视频/Trace 用于验证和证据。

## 断言与数据清理风险

- 列表加载可能受分页及数据状态影响；断言应优先使用表头和动态创建的目标房间，不依赖某个种子房间。
- 新增房间依赖有效公寓。通过页面下拉动态选择一个可见选项；若本地无可用公寓，应将其记录为环境前置条件，不猜测 ID。
- 删除清理应在 `finally` 中执行；删除成功用例不应重复删除。
- 编辑测试只编辑本次创建的数据。
